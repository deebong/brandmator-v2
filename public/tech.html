Multi-model naming engine

Brandmator is a browser-based naming tool that separates naming mechanisms from naming preferences. It combines word intelligence, model-specific generators, model-specific scoring, dictionary modes, brief relevance, user constraints and future domain intelligence.

ReactTypeScriptViteTailwindGitHub Pages

User flow

The public interface deliberately avoids exposing engine jargon. A new user follows one path:

1. Describe your brand
2. Choose a naming recipe
3. Choose an optional name feel
4. Shape the result: words, starts with, ends with
5. Generate
6. Refine vocabulary/domain settings only when needed

Internally, the recipe maps to one or more registered naming models. “Surprise me” is the public label for the Model 0 portfolio behavior. The model numbers remain useful for developers and documentation but are not required knowledge for normal use.

Prefix and suffix behavior

Starts with and Ends with are user-directed affixes plus hard output constraints. When a user enters f, the generator can construct f... candidates before enforcing the constraint, so the user does not need to search the results again. When a user enters ly, the generator can construct ...ly candidates. If a recipe cannot produce enough candidates under the requested shape and length, fewer results may be returned.

Real-word modes

Pure dictionary generation is exposed as a simple recipe. One-word mode returns untouched dictionary terms. Two-word mode joins untouched words without fusion and presents the brand in CamelCase while keeping the actual domain lowercase.

Feature inventory

Model 0 - Blend All

Portfolio/orchestrator mode combining the strongest results from the registered naming models.

Models 1-5

Fusion, brand spelling, prefix/initial, semantic wordform and experimental strategies with independent scoring.

Dictionary modes

Pure one-word and pure two-word combinations without fusion. Two-word names are shown in CamelCase while domain strings remain lowercase.

Brand brief

Local concept matching, simple aliases, inferred categories and relevance-weighted vocabulary selection. Generic business wording is not treated as a primary signal.

User controls

Categories, word sources, seed words, prefix, suffix, length range, result count and TLD selection remain available under Advanced controls.

Result tools

Search, model-aware score, model rationale, shortlist, CSV export, domain-only TXT export, pagination and result sorting.

UX

Light/dark theme, custom dropdowns, hidden native dropdown scrollbars, responsive layout, smooth pointer-driven sliders and footer back-to-top control.

SEO/GEO

Semantic HTML, metadata, canonical URL, Organization/SoftwareApplication JSON-LD, robots.txt and sitemap.

Architecture

Common model contract

type NamingModel = {
  id: ModelId
  name: string
  short: string
  description: string
  family: ModelFamily
  generate(context): ModelCandidate[]
  score(candidate, context): ModelScore
}

This is the extension point for future models. A model owns its own generation and scoring philosophy instead of being forced through a global rule set.

Model types

ModelPurposeTypical signals
Model 0 - Blend AllCombines registered models and diversifies the final portfolio.Model diversity, score, family diversity
Model 1 - Inventive FusionStrict coined forms from two source words.Phonetic flow, CV pattern, pronounceability, fusion method
Model 2 - Brand SpellingFlickr/censord/blastr-style transformations and familiar endings.Root retention, transformation quality, brand endings
Model 3 - Prefix & InitialPrefix + root and initial-letter structures such as fconserve.Root retention, prefix clarity, semantic fit
Model 4 - Semantic WordformRecognizer-friendly forms and useful semantic roots.Readability, semantic fit, root retention
Model 5 - ExperimentalLooser transformations intended to preserve creative outliers.Creativity, recognizability, compactness

Brand brief

The current brief layer is intentionally deterministic and browser-local. It tokenizes the description, recognizes short technology terms such as AI/ML/EV, ignores common filler and generic business terms, uses aliases and light stemming, infers categories, finds related library vocabulary and increases weighted selection for relevant terms.

The next AI-assisted layer can consume the same contract later for deeper concept extraction, audience, tone, forbidden clichés, differentiators and creative directions.

Naming styles

Style is a preference layer, not a replacement for the naming model. Presets include Balanced, More Inventive, More Meaningful, More Playful, More Professional and Short & Punchy. The selected style adjusts final preference weighting while the underlying model keeps its own generation and scoring philosophy.

Dictionary modes

Pure dictionary - One word

Returns untouched vocabulary entries. It does not imply availability or uniqueness. A common word can still be useful on another TLD.

Pure dictionary - Two words

Joins two untouched words without portmanteau fusion. The UI can present BlueOcean while the actual domain string remains blueocean.

Data layer

Current word sources are isolated into separate pools. The merged library retains source provenance, categories and weights. Sales vocabulary is a starter signal set derived from reported sales rather than a live sales feed.

Planned ingestion can replace or append these static pools without changing model code.

There is currently no analytics storage backend. A future Google Apps Script adapter can send these events to Google Sheets for aggregate product research without coupling storage to the naming engine.

Future domain availability architecture

Availability should be a separate service layer, not part of generation. The intended design is browser -> cache/batch service -> registrar/RDAP adapter. Recent checks can be cached and duplicate requests collapsed, reducing unnecessary provider traffic.

Roadmap

Now

Multi-model registry, model-specific scorers, brief relevance, dictionary modes, style preferences, responsive UX.

Next

Model-specific quality gates, stronger pronunciation analysis, better model portfolio allocation, name-family grouping.

Then

AI-assisted brief interpretation, availability cache/service, TLD comparison, conflict/trademark signals.

Later

User preference learning, scheduled sales-data ingestion, additional naming models and richer reporting.

How to add a future model

1. Create src/models/model6-your-style.ts
2. Implement the NamingModel contract.
3. Add generation rules.
4. Add a model-specific quality gate.
5. Add model-specific scoring dimensions.
6. Register the model in src/models/registry.ts.
7. Add documentation for the new model.
8. Let Model 0 discover it through the registry.

Do not modify the core generator to add model-specific logic. The registry is the intended extension point.

Development and deployment

The application is a Vite/React/TypeScript SPA. Local Node installation is not required for the intended workflow: GitHub Actions performs dependency installation and the production build, then deploys the generated dist artifact to GitHub Pages.

Important boundaries

  • Scores are heuristic model signals, not legal or trademark clearance.
  • Generated names are not guaranteed to be available on any TLD.
  • TLD cost metadata is an estimate and may change by registrar, registry, promotion and premium status.
  • The current brand brief is local deterministic relevance matching; it is not yet an LLM.
  • Sales vocabulary is a starter dataset, not a complete real-time sales feed.
